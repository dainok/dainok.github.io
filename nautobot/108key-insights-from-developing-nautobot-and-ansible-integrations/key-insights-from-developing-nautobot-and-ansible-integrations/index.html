    Key insights from developing Nautobot and Ansible integrations¶

    Andrea Dainese advanced ansible behind-the-scene nautobot

    Beyond the topics discussed in previous posts, my work on this project focused on four key areas:

    • The data structure of Nautobot
    • Nautobot's REST API
    • Integrating Ansible with Nautobot
    • Running Ansible playbooks from Nautobot

    Let's dive into the challenges encountered and the solutions omitted from previous posts.

    Nautobot's data structure¶

    Effectively using Nautobot requires careful planning of the data structure to avoid costly changes later. Understanding this structure allows for simplifications in automation scripts.

    Each object in Nautobot is identified by a UUID, such as 2170a207-43b2-422a-a90d-51a4908b85fb. This choice allows any attribute to be changed without issues. Since the device identifier is a UUID and not a name, we must consider:

    • Can two devices have the same name?
    • Can two interfaces on the same device have the same name?

    Quick tests reveal that the answer is no to both questions, allowing for safe simplifications in automation scripts.

    Django shell¶

    Nautobot is built on Django, a Python-based web application framework. Django provides a shell for easy interaction with the data structure.

    The decision had to be made whether to develop automations using the shell or the REST API.

    The shell can be invoked using the command:

    nautobot-server shell

    For example, to retrieve the list of interfaces associated with a device, you can use this simple script:

    from nautobot.dcim import models

models.Interface.objects.filter(device__name="MGMTSWITCH1")

    While this option is appealing, it is important to note that the shell is only available locally to the instance running Nautobot. In environments where Nautobot is running in containers, accessing the shell can be complex or impossible.

    REST API¶

    REST APIs are useful when well-documented, which is not the case with Nautobot. The documentation includes examples, and local installations provide API call documentation (http://localhost:8000/api/docs/)..) However, some features like filtering are poorly documented, requiring trial and error.

    The device_id filter worked, but device_name returned an error:

    {"device_name": ["Unknown filter field"]}

    After numerous attempts, I discovered a 2023 bug. Eventually, I realized the API filters are actually FilterSets, allowing device to filter by name or label.

    The equivalent code is:

    url = "http://localhost:8000/api/dcim/interfaces/?device=MGMTSWITCH1"

req = requests.get(url, headers=headers).json()

    Remember to handle pagination.

    Django shell o REST API¶

    Deciding between the shell and REST API, I chose the REST API for broader compatibility despite the difficulties.

    Integrating Ansible with Nautobot¶

    network.toCode() provides a specific Ansible collection for Nautobot. I needed a solution to use Nautobot as an Ansible inventory without creating one from scratch.

    The plugin documentation offers a good starting point with examples.

    The challenge is defining a data structure that includes:

    • Ansible-specific parameters (ansible_connection, ansible_network_os, ansible_host, ansible_user, ansible_ssh_pass)
    • A group identifying devices
    • A list of interfaces with profiles for each device

    Three options exist:

    • The inventory contains all necessary information from Nautobot.
    • Playbook defines information except for the group with correct variables.
    • A mix of both.

    I opted to move information to Nautobot to experiment with custom fields. In practice, usernames and passwords are stored in a vault; for simplicity, I hardcoded them in the playbook.

    After testing, I found the correct combination. Two custom fields map to variables:

    compose:
  ansible_connection: custom_fields.connection
  ansible_network_os: custom_fields.network_os

    Each device is associated with three groups based on attributes:

    keyed_groups:
- key: device_types
  prefix: type
- key: manufacturers
  prefix: manufacturers
- key: location
  prefix: location

    compose and keyed_groups are standard Ansible features that required some trial and error. I used the following command to test:

    ansible-inventory -i inventory.yml --list

    The Ansible Playbook¶

    Creating an optimized Ansible playbook requires experience. I reused a previously developed role with slight modifications.

    First, I read the configuration from Nautobot and created two data structures:

    • interface_profiles: maps interfaces to profiles.
    • interface_cfgs: contains the data structure for the ios_interfaces module.

    This approach was necessary as the ios_l2_interfaces module does not support all needed parameters. Using the ios_config module for interface configuration and ios_interfaces for specific parameters (description and status) was the solution.

    This results in a simple CLI command list that any network engineer can read and modify:

    lines:
- switchport access vlan 53
- switchport voice vlan 54
- no cdp enable
- no lldp receive
- no lldp transmit
- spanning-tree bpduguard enable
- spanning-tree portfast edge
- switchport mode access
- switchport nonegotiate

    I used Jinja to create the data structure for better performance:

    ansible.builtin.set_fact:
  interface_profiles: >-
    {
      {% for interface_name, profile in interface_profiles.items() %}
        {% if interface_name == interface_limit %}
          "{{ interface_name }}": "{{ profile }}",
        {% endif %}
      {% endfor %}
    }

    Verify the data structure as JSON using the debug command to avoid issues like missing commas:

    ok: [MGMTSWITCH1] => {
"msg": "{\n\"GigabitEthernet1/0/44\": \"interface_access\"\n\"GigabitEthernet1/0/45\": \"
interface_isl\"\n\"GigabitEthernet1/0/47\": \"interface_trunk\"\n}"

}

    Once corrected

    ok: [MGMTSWITCH1] => {
    "msg": {
        "GigabitEthernet1/0/44": "interface_access",
        "GigabitEthernet1/0/45": "interface_isl",
        "GigabitEthernet1/0/47": "interface_trunk"
    }
}

    The next step is enabling playbook execution for a specific interface:

    ./playbook-interface-configuration.yml --extra-vars interface_limit=GigabitEthernet1/0/47

    I cleaned the data structures to keep only the filtered element. Profile association is done using include_tasks, optimal for network engineers who deal with profiles for each interface.

    Finally, description and interface status are configured using the ios_interfaces module, simplifying shutdown and no shutdown command management.
