    The Ansible role breakdown¶

    Andrea Dainese advanced ansible nautobot

    Now, we need to translate the interface roles defined in Nautobot into specific configurations for the switches. To achieve this, we will create an Ansible role that utilizes the inventory described in the previous post to configure the interfaces of each device.

    Fetch Running Configuration¶

    First, we retrieve the current running configuration from the switch:

    - name: GETTING RUNNING CONFIGURATION
  cisco.ios.ios_command:
    commands:
      - show running-config
  register: show_running_config

    Optimizing show running-config improves overall performance.

    Create data structures¶

    Next, we generate data structures with necessary details from Nautobot:

    - name: SETTING INTERFACE PROFILES
  ansible.builtin.set_fact:
    interface_profiles: >-
      {
        {% for interface in interfaces %}
          {% if interface.role %}
            "{{ interface.name }}": "{{ interface.role.name }}",
          {% endif %}
        {% endfor %}
      }
    interface_cfgs: >-
      [
        {% for interface in interfaces %}
          {% if interface.role %}
            {
              "name": "{{ interface.name }}",
              {% if interface.enabled %}
                "description": "{{ interface.description }} ({{ interface.role.name }})",
                "enabled": true,
              {% else %}
                "enabled": false,
              {% endif %}
            },
          {% endif %}
        {% endfor %}
      ]
    • interface_profiles links each interface to its profile.
    • interface_cfgs holds configurations for the ios_interfaces module .

    Interfaces are processed only if they have an associated profile.

    Limit data structure (optional)¶

    Optionally, we can limit the data structure to a single interface via command line:

    - name: FILTERING INTERFACES
  ansible.builtin.set_fact:
    interface_profiles: >-
      {
        {% for interface_name, profile in interface_profiles.items() %}
          {% if interface_name == interface_limit %}
            "{{ interface_name }}": "{{ profile }}",
          {% endif %}
        {% endfor %}
      }
    interface_cfgs: >-
      [
        {% for interface in interface_cfgs %}
          {% if interface.name == interface_limit %}
            {{ interface }},
          {% endif %}
        {% endfor %}
      ]
  when: interface_limit is defined

    Apply interface profile configuration¶

    For each interface, an external configuration file is included:

    - name: ATTACHING PROFILE TO INTERFACE
  ansible.builtin.include_tasks: "profile_{{ interface.value }}.yml"
  with_dict: "{{ interface_profiles }}"
  loop_control:
    loop_var: interface

    The profile file uses the ios_config module to apply configuration commands:

    - name: "APPLYING PROFILE ISL TO INTERFACE {{ interface.key }}"
  cisco.ios.ios_config:
    config: "{{ show_running_config.stdout.0 }}"
    lines:
      - switchport trunk encapsulation dot1q
      - switchport mode trunk
      - switchport nonegotiate
      - udld port aggressive
    parents: "interface {{ interface.key }}"
    before: "default interface {{ interface.key }}"

    This step is the slowest, so optimizations are crucial.

    Set interface description and state¶

    Finally, we apply the prepared configuration data:

    - name: "SETTING INTERFACE STATUS"
  cisco.ios.ios_interfaces:
    config: "{{ interface_cfgs }}"
    state: merged

    This task manages the interface state (shutdown and no shutdown) using the native module.

    Running the playbook¶

    Execute the playbook on all devices or limit it to a specific interface:

    ./playbook-interface-configuration.yml
./playbook-interface-configuration.yml --extra-vars interface_limit=GigabitEthernet1/0/47 --limit MGMTSWITCH1

    By following these steps, you'll efficiently automate your network interface configurations using Ansible and Nautobot.

    The Ansible role can be downloaded from GitHub.
