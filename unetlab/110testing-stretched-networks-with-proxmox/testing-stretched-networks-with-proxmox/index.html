    Testing stretched networks with Proxmox¶

    Andrea Dainese advanced proxmox unetlab

    Let's explore how Proxmox's SDN functionality works. We'll use the SDN structure to implement extended L2 networks, enabling us to run labs across multiple hosts.

    Create an SDN Zone¶

    First, create a zone:

    pvesh create /cluster/sdn/zones -type=vxlan -zone=unlzone1 -peers=172.25.82.157,172.25.82.158 -ipam=pve
pvesh set /cluster/sdn/zones

    In the peers list, add all the IP addresses of the Proxmox hosts.

    Create a Bridge Associated with the Zone¶

    Next, create a bridge linked to the zone for connecting the nodes:

    pvesh create /cluster/sdn/vnets -vnet=unlnet1 -tag=1000004 -zone=unlzone
pvesh set /cluster/sdn/zones

    Then, associate the network with the nodes as shown in the previous steps.

    If configured correctly, nodes running on different hosts should be able to ping each other, using both native VLAN and tagged VLAN.

    Design Considerations¶

    From a design perspective, we need to decide how to manage zones and networks within UNetLab: should we create a single zone with all Vnets, or a zone for each Vnet?

    According to the official documentation,) a zone defines a virtually separated network. The documentation lacks detail, so we need to understand the constructs created at the OS level.

    When creating the zone, we specified the IP addresses of the Proxmox hosts sharing that zone. This configuration is written to /etc/pve/sdn/zones.cfg and generates the /etc/network/interfaces.d/sdn file. No network namespace configurations (ip netns) are present.

    We can deduce that the zone is a Proxmox-defined structure that translates into VXLAN interfaces. Since UNetLab won't use L3 networks, we can use a single zone for the entire UNetLab cluster.

    Troubleshooting¶

    During my initial test, the two VyOS nodes couldn't communicate. By connecting to the two Proxmox servers via SSH, we can see how the SDN configuration translates at the OS level.

    Network interfaces of the nodes are associated with a bridge:

    brctl show unlnet3

    bridge name     bridge id               STP enabled     interfaces
unlnet3         8000.6659fe6b9723       no              tap10001i1
                                                        vxlan_unlnet3

    The TAP interface belongs to the node, while the VXLAN interface allows communication with nodes on other hosts.

    Check the forwarding table for frames with:

    bridge fdb show | grep vxlan

    66:59:fe:6b:97:23 dev vxlan_unlnet3 vlan 1 master unlnet3 permanent
66:59:fe:6b:97:23 dev vxlan_unlnet3 master unlnet3 permanent
00:00:00:00:00:00 dev vxlan_unlnet3 dst 172.25.82.158 self permanent
ba:2f:72:71:47:0a dev vxlan_unlnet4 vlan 1 master unlnet4 permanent
ba:2f:72:71:47:0a dev vxlan_unlnet4 master unlnet4 permanent
00:00:00:00:00:00 dev vxlan_unlnet4 dst 172.25.82.158 self permanent

    The MAC addresses on the right should match the network interfaces of nodes running on the remote host. In my case, the remote VyOS node had its network interfaces reversed, resulting in an incorrect connection.
