    UNetLab v2 addressing limitations¶

    Andrea Dainese beginner unetlab

    In recent years, my focus has shifted towards network automation. I still need a unified network emulator platform, but the prerequisites have evolved. Before diving into the new requirements, let's highlight the limitations of UNetLab:

    • Per Host Pod Limit: Each host can run up to 256 independent pods due to the console port limit.
    • Per Lab Node Limit: Each pod/lab can run up to 127 nodes due to the console port limit.
    • Per User Pod Limit: Each user can run only one pod/lab at a time due to the console port limit.
    • Single Host: No support for distributed installations of UNetLab (OVS can be used, but many frame types are filtered by default).
    • Config Management: Using expect scripts for getting and putting startup-configs is slow, non-predictive, and cannot cover all node types.
    • No Support for Dynamips Serial Interfaces.
    • No Topology Changes: Topology changes are not allowed while the lab is running, by design.

    The console port limit exists because each node console has a fixed port calculated as follows:

    ts_port = 32768 + 128 * tenant_id + device_id

    Additionally, no more than 512 IOL nodes can run in the same lab because the device_id must be unique for each tenant.

    UNetLab v2 must address these issues and meet new requirements:

    • Run a distributed lab (across local or geographically distributed nodes).
    • Support an unlimited number of nodes in a lab.
    • Allow each user to customize a lab without affecting the original copy.
    • Link serial interfaces between IOL and Dynamips.
    • Configure nodes via Ansible/NAPALM/other tools.

    I knew how to create a distributed network emulator but needed an easy way to run nodes within a dedicated namespace. The answer came from vrnetlab: using Docker.

    Due to the limitations of UNetLab, I decided to rewrite it from scratch. Although EVE-NG, a fork of UNetLab, works to overcome these limitations, I pursued a new path.

    UNetLab v2 Architecture¶

    The architecture may seem complex, but it was straightforward to implement.

    UNetLab v2 was based on:

    • Docker: Controllers, routers, and lab nodes run inside Docker containers.
    • Python: Replaces C, PHP, and Bash with Python 3.
    • Python-Flask + NGINX: Implements and exposes APIs.
    • Memcached: Caches authentication for better user experience.
    • Celery + Redis: Manages asynchronous long tasks in the background.
    • MariaDB: Stores all data, user information, and running labs.
    • Git: Manages version control for original labs.
    • jQuery + Bootstrap: Implements the UI as a single-page application.
    • iptables + Linux bridge: Allows SSH connections to just-started lab nodes.
    • IOL, QEMU, and Dynamips: Runs lab nodes.

    A UNetLab v2 cluster must have at least one node, which can be physical or virtual. The first node is the master, containing a controller and a router, while additional nodes contain only routers. Each node also runs multiple lab nodes. Controllers, routers, and lab nodes are Docker instances.

    The controller container:

    • Exposes the web UI and APIs to user clients, routers, and lab nodes.
    • Receives registration requests from routers and lab nodes.
    • Manages lab nodes via routers.
    • Contacts lab nodes via Ansible/NAPALM/etc.
    • Provides routing tables to routers.
    • Accessible via SSH using port 2222.

    The router containers:

    • Register with the controller.
    • Expose Docker Remote API and lab node API.
    • Obtain routing tables from the controller.
    • Route lab packets between nodes and routers.
    • Ensure connectivity between the controller and remote lab nodes via OpenVPN.

    The node containers:

    • Register with the controller.
    • Run emulated nodes (IOL, Dynamips, or QEMU).
    • Bind a management interface of emulated nodes to a local bridge.
    • Route packets between the local router and the emulated node for non-management interfaces.
    • Manage emulated links (up/down).

    Since the controller and routers know both inside and outside IP addresses, users can deploy UNetLab v2 nodes anywhere (in the same LAN, AWS, Google Compute Engine, Azure, behind a firewall). Each UNetLab v2 cluster requires the following ports:

    • TCP: 2222: SSH connection to the controller.
    • TCP: 80/443: HTTP/HTTPS requests to the controller.
    • TCP: 5443: HTTPS requests to the router.
    • UDP: 5005: Routed packets between different UNetLab v2 nodes.
    • UDP: 1194: Network reachability between the controller and remote lab nodes.

    UNetLab v2 was never completed, but the source code is available on GitHub.
