    Ansible statements¶

    Andrea Dainese advanced ansible

    If you’ve got some experience with programming languages, you might find Ansible's constructs a bit clunky. But no worries, let's break them down with some practical examples to make things clearer.

    Conditionals (if, then, else)¶

    In Ansible, the if-then-else construct is simplified to a single word: when.

    - ansible.builtin.command: /sbin/shutdown -t now
  when: ansible_facts['os_family'] == "Debian"

    Unlike traditional languages, there’s no direct else or elif. You’ll handle them all with separate when statements and the right expressions.

    If you’ve got a bunch of conditions that all need to be true at the same time (logical AND), you can list them out:

    - ansible.builtin.command: /sbin/shutdown -t now
  when:
    - ansible_facts['distribution'] == "CentOS"
    - ansible_facts['distribution_major_version'] == "6"

    Each variable in Ansible can be one of the following types:

    • List
    • Dictionary
    • Boolean (True/true/yes/on or False/false/no/off)
    • Integer
    • Float
    • String (if it’s wrapped in quotes or doesn’t fit the above types)

    Ansible heavily relies on Jinja, which adds a bit more complexity to the mix. Any variable created using Jinja is treated as a string, and you'll often need to convert it before use. But sometimes Ansible takes care of this for you, like when it automatically converts a string containing JSON into a list or dictionary when used in a loop.

    Here’s a quick breakdown to help you navigate this:

    • Variables can be either defined or undefined.
    • A defined variable might be empty (None) or have some data.
    • The variable’s type depends on the data it holds (Ansible uses weak typing).
    • Ansible often creates strings using Jinja, which may require conversion.
    • Ansible will automatically convert strings into lists or dictionaries when needed.
    • Before performing mathematical operations, it’s a good habit to explicitly convert variables using Jinja filters like | int or | float.

    The best approach? Always double-check how Ansible handles different cases. You can use debug tools to inspect the type and value of your variables:

    - ansible.builtin.debug:
    msg: "Type of var is {{ var | type_debug }}"
- ansible.builtin.debug:
    msg: "Content of var is {{ var }}"

    For more details and examples, check out the official Ansible documentation.

    Blocks¶

    A block is a group of tasks. Blocks can be used to:

    • Group tasks that share the same when condition.
    • Handle errors using the rescue and always directives.
    - block:
    - ansible.builtin.debug:
        msg: "{{ value | int }}"
  rescue:
    - ansible.builtin.debug:
        msg: "Value is not defined"

    Loops¶

    A loop can be applied to lists or dictionaries to iterate over elements and perform one or more actions. There are two important considerations:

    • Using loops impacts performance directly.
    • A loop can only be applied to a single action, not a group of actions.

    For simplicity, let’s look at three common approaches and leave deeper insights for the official documentation.

    With with_items, you can iterate over a list of elements. In each iteration, by default, the item variable takes on the value of each list element:

    - ansible.builtin.debug:
    msg: "{{ item }}"
  with_items:
    - red
    - green
    - blue

    With with_dict, you can iterate over a dictionary. In each iteration, item.key and item.value will hold the key and value of each key-value pair in the dictionary:

    - ansible.builtin.debug:
    msg: "{{ item.value }} is {{ item.key }}"
  with_dict:
    red: tomato
    green: grass
    blue: sky

    Ansible later standardized loops with the loop construct. However, out of habit and convenience, I still tend to use with_items and with_dict, which feel more straightforward to me. That said, loop can be more useful for more complex scenarios.

    Nested Loops¶

    We've already seen how to implement loops in Ansible. Sometimes, however, you might need to implement loops within loops (nested loops) or loops over groups of tasks. In both cases, the solution is similar and involves using external files:

    - ansible.builtin.include_tasks: sub_task1.yml
  with_items:
    - macos
    - windows
    - linux
  loop_control:
    loop_var: os_item

    In this example, we iterate over a list and call an external task file sub_task1.yml. All the tasks in this file can use the variable os_item, which takes on each value from the os list.

    When I need to call an external task file, I always prefer to explicitly specify the variable value. This avoids confusion and prevents the variable from being overwritten by any loops inside the external file.

    Until¶

    Finally, let's look at how to execute a task until the desired result is achieved:

    - ansible.builtin.shell: /usr/bin/foo
  register: result
  until: result.stdout.find("ready") != -1
  retries: 5
  delay: 10

    In this example, we run a (fictional) command until the output contains the word ready. The execution stops with an error after 5 failed attempts, with a 10-second interval between each try.

    Configuring NTP with ios_config¶

    Let's explore how to configure NTP peers using the ios_config module. Before writing the playbook, we should review the official documentation and consider how we would configure NTP peers manually. Here’s the typical process:

    • Configure the NTP servers.
    • Verify the NTP servers configured on the device.
    • Remove any NTP servers configured on the device that are not in the desired NTP server list.

    Now, we need to write a role that performs these three tasks exactly as described.

    First, we’ll refer to the official documentation and add the missing NTP peers:

    - cisco.ios.ios_config:
    lines:
      - "ntp peer {{ ntp_server_1 }}"
      - "ntp peer {{ ntp_server_2 }}"

    Next, we need to remove any unnecessary NTP peers. When working manually, we would retrieve the running-config to check for any unknown addresses. In Ansible, we do something similar:

    - cisco.ios.ios_command:
    commands:
      - "show running-config | include ntp peer"
  register: show_run_ntp_peer

    The register option saves the output into a variable that we define. If we print this variable using debug, we can analyze its structure.

    The output is in JSON format and contains the raw output (stdout) and the output split into lines (stdout_lines). Both are arrays because multiple commands can return output simultaneously.

    For convenience, we'll extract only the NTP peer IP addresses into specific variables:

    - ansible.builtin.set_fact:
    current_ntp_peers: "{{ show_run_ntp_peer['stdout'][0] | regex_findall('^ntp peer .*$', multiline=True) | regex_replace('ntp peer ', '') }}"
    expected_ntp_peers:
      - "{{ ntp_server_1 }}"
      - "{{ ntp_server_2 }}"

    The current_ntp_peers variable stores all lines starting with ntp peer. Before saving, the prefix ntp peer is removed, leaving us with a list of only the NTP peer IP addresses.

    Note: If any of our IPs are configured as preferred, the configuration would become more complex.

    At this point, we need to compare the current configuration and remove any unnecessary peers. Specifically, we compare each element of the configuration, and if it is not part of the expected NTP peer list, we remove it:

    - name: REMOVING NTP PEERS
  cisco.ios.ios_config:
    lines:
      - "no ntp peer {{ item }}"
  with_items: "{{ current_ntp_peers }}"
  when: item not in expected_ntp_peers

    The code above loops (with_items) through the current_ntp_peers list, and each item is compared with the expected_ntp_peers list. If (when) the address is not found, it is removed using the ios_config module.

    This playbook could be optimized for efficiency, but it’s designed to be more readable and understandable.
